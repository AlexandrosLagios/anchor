Audit of the Anchor website (`apps/web`) for later fixes. No product code was changed in this pass.

- **Commit:** `5dfefce588eeb23295bd6d3fa8de3386473a1021` (`Finish signup after the family step and land on continuous upload plus Ask Anchor chat.`)
- **Engine:** axe-core 4.13.0 in headless Google Chrome (Playwright `channel: 'chrome'`). Viewports 1280×900 and 320×800.
- **Rules:** `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` (WCAG 2.0 and 2.1, Level A and AA).
- **Server:** `astro preview` of the static build at `http://127.0.0.1:4321`.

## Verdict

`pnpm a11y:web` scans each public route once, at the default 1280px viewport, with the cookie banner open and dismissed. That gate is clean: **0 axe violations** on those 20 scans.

The same pages fail WCAG 2.1 AA in states the gate does not open: a gold primary link whose text matches its background, the demo chat after it starts scrolling, the mobile chat tab, and the signed-in family page at 320px.

## Fix 1 — primary links inside `.prose` are the same color as their fill

**Rule:** `color-contrast` (axe marks it **incomplete**, with the text “Element has a 1:1 contrast ratio”)
**Criterion:** WCAG 1.4.3 Contrast (Minimum) (AA)
**Help:** https://dequeuniversity.com/rules/axe/4.13/color-contrast

**When it appears**

On `/how-it-works` and on the 404 page, at 1280px and 320px, banner open or dismissed.

Computed style of `a.btn.btn-primary`:

- Foreground `rgb(201, 167, 122)` (`#c9a77a`)
- Background `rgb(201, 167, 122)` (`#c9a77a`)
- Ratio **1:1** (needs **4.5:1**)

The homepage “Get started” control is `a.slate-btn.slate-btn-primary` and measures `#1a1a1a` on `#c9a77a` (about 7.8:1). It passes.

**Where**

- Markup: `<a class="btn btn-primary" href="/family">Get started</a>` inside `<article class="prose">` in `apps/web/src/pages/how-it-works.astro`. The 404 page has the same pattern for “Back to Anchor” in `apps/web/src/pages/404.astro`.
- CSS: `.prose a` in `apps/web/src/styles/tokens.css` sets `color: var(--brand)`. That selector (0, 1, 1) beats `.btn-primary` (0, 1, 0), which sets `color: #1a1a1a` and `background: var(--brand)`.

**Suggested fix**

Keep link color off button anchors:

```css
.prose a:not(.btn) {
  color: var(--brand);
  font-weight: 600;
}
```

Re-measure the two anchors. Resting color should be `#1a1a1a` on `#c9a77a`.

**Gate follow-up**

`pnpm a11y:web` will stay green until this is a violation rather than an incomplete result. Add an assertion on these two anchors’ computed `color` and `backgroundColor`, or treat a 1:1 incomplete `color-contrast` node as a failure.

## Fix 2 — selected demo tab at 320px

**Rule:** `color-contrast` (serious)
**Criterion:** WCAG 1.4.3 Contrast (Minimum) (AA)

**When it appears**

`/app` at 320×800, on first paint, banner open or dismissed. The selected tab is “Family group”. After the private chat is opened, the selected tab is “Nikos, in private” and fails the same way.

- Foreground `#f4fffc`
- Background `#c9a77a`
- 15.2px, bold
- Ratio **2.21:1** (needs **4.5:1**)

At 1280px `.mvp-switch` is `display: none`, so axe does not see the tab. That is why the gate passes.

**Where**

`apps/web/src/components/MvpDemo.css`, inside `@media (max-width: 52rem)`:

```css
.mvp-switch button[aria-selected='true'] {
  background: var(--brand);
  color: #f4fffc;
  border-color: var(--brand);
}
```

**Suggested fix**

Use the same sand-button text as `.btn-primary`:

```css
.mvp-switch button[aria-selected='true'] {
  background: var(--brand);
  color: #1a1a1a;
  border-color: var(--brand);
}
```

## Fix 3 — speaker names in the demo chat

**Rule:** `color-contrast` (serious)
**Criterion:** WCAG 1.4.3 Contrast (Minimum) (AA)

**When it appears**

On `/app`, after clicking **Send the photo**, **Yes, I’ll take part**, and **A little later — bring it back**. It is still there after **Use a sample line**. At 320px, switch to the “Nikos, in private” tab before the private buttons are visible. Earlier phases pass.

| Name | Foreground | Background | Ratio |
| --- | --- | --- | --- |
| Sofia | `#6e3000` | `#2a3328` | 1.30:1 |
| Nikos | `#003f61` | `#332c26` | 1.23:1 |
| Anchor | `#084740` | `#2a2a2a` | 1.35:1 |

All three are 12.48px bold. They need **4.5:1**.

**Where**

- Markup: `<span class="who">` in `apps/web/src/components/MvpDemo.tsx`.
- CSS: `.sofia .who`, `.nikos .who`, `.anchor .who` in `apps/web/src/components/MvpDemo.css`. The bubble fills are the dark tokens `--bubble-family`, `--bubble-athina`, and `--bubble-anchor`.

**Suggested fix**

Set the names to `color: var(--ink)` (`#f2f0eb`). That is light text on those dark bubbles and clears 4.5:1. Re-run axe on the “bring it back” state.

## Fix 4 — chat logs are not keyboard-scrollable

**Rule:** `scrollable-region-focusable` (serious)
**Criteria:** WCAG 2.1.1 Keyboard (A), 2.1.3 Keyboard (No Exception) (A)
**Help:** https://dequeuniversity.com/rules/axe/4.13/scrollable-region-focusable

**When it appears**

1. Demo private log (`.chat-log`) after the three clicks in Fix 3, at 1280px and 320px. The group log does not fail in that state.
2. Ask Anchor log (`.family-chat-log`) on the signed-in `/family` record once the log is taller than `max-height`. One welcome line does not overflow (`scrollHeight` 107, `clientHeight` 107), so first paint passes. Filling the log makes it fail (`scrollHeight` 1213, `clientHeight` 446).

**Where**

- `div.chat-log` with `role="log"` in `apps/web/src/components/MvpDemo.tsx`. Layout: `.chat-shell .chat-log` in `apps/web/src/components/MvpDemo.css` sets `max-height: min(26rem, 52vh)` on top of `.chat-log { overflow: auto }`.
- `div.family-chat-log` with `role="log"` in `apps/web/src/components/FamilyChat.tsx`. Layout: `.family-chat-log` in `apps/web/src/components/FamilyRecord.css` sets `max-height: min(28rem, 55vh)` and `overflow: auto`.

Neither region has `tabindex`, and the messages inside are not focusable. A keyboard user cannot move the overflow.

**Suggested fix**

Prefer letting the page scroll and dropping the inner `max-height` / `overflow: auto`, so there is no nested scrollport.

If the pane must stay a fixed height, make the log focusable and name it, for example `tabIndex={0}` and `aria-label="Private chat with Anchor"` (and `aria-label="Conversation with Anchor"` on `.family-chat-log`). `role="log"` is a live region. It is not a keyboard scroll target.

**Gate follow-up**

Extend `apps/web/scripts/a11y-check.mjs` so `/app` is scanned after those three clicks, and so `/family` is scanned with a session that has finished registration and a chat log taller than the max height.

## Fix 5 — memory file input scrolls sideways at 320px

**Criterion:** WCAG 1.4.10 Reflow (AA)
**Not an axe rule.** Measured in Chrome at 320×800, cookie banner dismissed, registration marked complete in `sessionStorage`.

**When it appears**

Signed-in `/family` only. `documentElement.scrollWidth` is **416px** against a **320px** viewport. The registration steps (before completion) stay at 320px. The public pages, including `/family` before sign-in, stay at 320px.

**Where**

The overflowing element is `input.reg-file` in `apps/web/src/components/MemoryUpload.tsx` (“Photo or voice note”). Its border box is **375px** wide. `.reg-file` in `apps/web/src/components/RegisterFlow.css` only sets `font-weight: 400`, so the native file control keeps its intrinsic width.

**Suggested fix**

Constrain the control to the column and re-measure `scrollWidth` at 320px:

```css
.reg-field {
  display: grid;
  min-width: 0;
  max-width: 100%;
}

.reg-file {
  display: block;
  width: 100%;
  max-width: 100%;
}
```

If the native control still refuses to shrink, visually clip it and expose a real `<button>` that opens the file picker, with an accessible name of “Photo or voice note”. Axe will not catch a regression here. The check has to be a viewport measurement.

## Fix 6 — step indicator disagrees with the step list

Not an axe failure. On `/family`, the kicker says `Step {step} of 3` while `STEPS` is `Account`, `Bot`, `Family`, `Memory` (four items) in `apps/web/src/components/RegisterFlow.tsx`. The list is exposed as `ol.reg-steps` with `aria-label="Registration steps"`. Memory is the upload and chat view after registration, and that view does not render the list, so “Memory” never becomes `aria-current="step"`.

**Suggested fix**

Say “Step n of 4” and keep the indicator on the upload view, or remove “Memory” from the list that is shown during the first three steps.

## Design studies (not in the live nav)

`/designs/slate` loads `slate.css` and does not load `tokens.css`, so `body` stays white while the type uses the light Slate colors.

| Node | Pair | Ratio | Needs |

| `p.slate-line` | `#f2f0eb` on `#ffffff`, 28px | 1.13:1 | 3:1 |
| `p.slate-support` | `#c4bfb5` on `#ffffff`, 17px | 1.83:1 | 4.5:1 |
| `a.slate-btn-ghost` | `#f2f0eb` on `#ffffff`, 16px | 1.13:1 | 4.5:1 |
| `a.slate-link` | `#c9a77a` on `#ffffff`, 16px | 2.26:1 | 4.5:1 |

At 320px the page also overflows to **374px**. The widest node is `a.slate-btn.slate-btn-primary` (“Try the demo”) at 346px. The live homepage uses the same class names through `BaseLayout` (which loads `tokens.css`) and does not overflow.

`/designs/ink`: three `span.ink-action-index` elements (`01`, `02`, `03`) are `aria-hidden="true"` and still visible. `.ink-action-index` sets `opacity: 0.55`, which axe resolves as `#787878` on `#ffffff`, 12px, ratio **4.41:1** (needs **4.5:1**). Darken the index color to about `#767676` or drop the opacity. Because they are `aria-hidden`, this is a visual contrast bug.

`/designs/linen` and `/designs/mist`: 0 violations, no horizontal scroll, at both widths.

`/designs/quiet`: axe incomplete because the body is a gradient. Declared `--quiet-ink` `#1a1917` on the lightest stop `#f7f4ed` is dark text on near-white paper and clears 4.5:1.

## What passed

Public routes, each with the cookie banner open and with it dismissed (Accept), at 1280×900 and at 320×800, except the `/app` tab failure at 320px:

`/`, `/how-it-works`, `/app`, `/family`, `/my-data`, `/privacy`, `/terms`, `/cookies`, `/sitemap`, and a missing URL that renders the 404 page.

`/family` interactions that passed axe at 1280px with the banner dismissed:

- Create an account (privacy policy, email, password, acceptance boxes)
- Sign in
- Messenger step (Telegram, WhatsApp, and the Viber hint when `PUBLIC_VIBER_ADD_LINK` is empty)
- Create a family
- Finished registration: “Add memories” file field and “Ask Anchor” with the single welcome line

Home (`/`) uses solid `#1a1a1a`, so axe could measure contrast and reported no violations. Body text `--ink` `#f2f0eb` and muted `#c4bfb5` on that background both clear 4.5:1. Sand buttons with text `#1a1a1a` on `#c9a77a` also clear it, when `.prose a` does not override the text color.
