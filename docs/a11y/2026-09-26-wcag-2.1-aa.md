Axe files a 1:1 contrast ratio as **incomplete**, and the high-contrast setting is outside the gate.

## What passed

- Public pages at 1280×720, 390×844, and 320×640, consent dismissed: 0 axe violations. No horizontal overflow on those pages at 320px.
- Each public page has `lang="en"`, one `h1`, a document title, and a “Skip to content” link. No skipped heading levels on the desktop consent-dismissed pass.
- Keyboard sample on `/` at 1280×720: first Tab stop is “Skip to content”, then the header. Focus ring is `2px solid rgb(68, 61, 255)`.
- No images missing `alt`. No unlabelled inputs on the scanned states.
- Email registration, the new surface on this commit: `/family` “Sign in” and “Create an account” both have 0 violations. Email, name, password, and the two consent checkboxes are wrapped in `<label>`s. The privacy policy block grows with the page (`scrollHeight` equals `clientHeight`), so it is not an unreachable scroll region.
- `/my-data` signed out, and signed in with a local account token (download, sign out, optional Telegram): 0 violations.
- Accessibility panel open, default theme, on `/`: 0 violations.
- Design studies `/designs/linen` and `/designs/mist`: 0 violations. `/designs/slate` at 1280×720: 0 violations.

## Fix later

### 1. Primary buttons inside `.prose` — WCAG 1.4.3 Contrast (Minimum)

`.prose a` in `apps/web/src/styles/tokens.css` sets `color: hsl(var(--primary))` and wins over `.btn-primary`, so “Get started” and “Back to Anchor” render as primary-colored text on a primary background. Computed color and background are both `rgb(68, 61, 255)`. Axe reports this as incomplete (“1:1 contrast ratio”), which is why the gate stays green. Normal text needs 4.5:1.

| Page | Control | States where it showed up |
| --- | --- | --- |
| `/how-it-works` | “Get started” (`a.btn.btn-primary`) | consent open and dismissed, 1280, 390, and 320 |
| `/404` | “Back to Anchor” (`a.btn.btn-primary`) | consent open and dismissed, 1280, 390, and 320 |

Suggested fix: `.prose a.btn` (and `.prose a.slate-btn`) should keep the button text color, `hsl(var(--background))` in the default theme. Do not let `.prose a` override button colors.

### 2. High contrast display setting — WCAG 1.4.3

`html.a11y-contrast` in `apps/web/src/styles/tokens.css` swaps the page to a dark background (`#050316`) and paints links with `--primary` (`#443dff`). That pair is **3.25:1**. Normal text needs 4.5:1. Primary buttons use `color: hsl(var(--background))`, and in this mode `--background` is the dark color, so the label is `#050316` on `#443dff`, also **3.25:1**. Light text `#fbfbfe` on that same primary is about **6.06:1**. A lighter link color such as `#a8a4ff` on `#050316` is about **9.14:1**.

The class is applied from `anchor-a11y-prefs-v1` before paint. The sitemap tells people the site aims for WCAG 2.1 AA and points them at this control.

Repeated pairs:

- Links and body accents: 3.25:1, `#443dff` on `#050316`.
- Primary buttons (“Start Remembering Together”, “Sign in with email”): 3.25:1, `#050316` on `#443dff`.
- `/app` chips in the demo (step labels and similar): **1.21:1**, `#f3f2fe` on `#dddbff`.
- `/family` current step label: **1.29:1**, `#fbfbfe` on `#dddbff`.
- Accessibility panel open on `/` in high contrast adds the inactive “Larger” control at **1.29:1** (`#fbfbfe` on `#dddbff`) and the active “Default” control at **3.25:1** (`#050316` on `#443dff`).

Suggested fix: in `html.a11y-contrast`, set link color to a lighter violet that clears 4.5:1 on `#050316`, set `.btn-primary` / `.slate-btn-primary` text to the light text token (not the swapped `--background`), and give accent chips (`#dddbff`) a dark label.

### 3. Demo after a sample voice note — WCAG 1.4.3 and 2.1.1 Keyboard

Static `/app` passes. After “Send the photo” → “Yes, I’ll take part” → “A little later — bring it back” → “Use a sample line”:

- `.voice-tag` (“Voice note”) in `apps/web/src/components/MvpDemo.css` is **3.94:1** (`#443dff` on `#cbc8ff`, 12.48px, bold). Needs 4.5:1.
- The private `.chat-log` (`role="log"`, `overflow: auto`) fails `scrollable-region-focusable` (WCAG 2.1.1 / 2.1.2 related keyboard access to the scrollable region). It should be focusable (`tabindex="0"`) with an accessible name, or the messages inside need to be in the tab order.

`.family-chat-log` uses the same overflow pattern and was not filled, because that needs a signed-in family API.

### 4. Design exploration `/designs/ink` — WCAG 1.4.3

Not linked from the public header, footer, or sitemap. Three index labels (`.ink-action-index`, `opacity: 0.55` in `apps/web/src/components/designs/ink/ink.css`) are **4.41:1** (`#787878` on `#ffffff`, 12px). Needs 4.5:1. Same failure at 320×640.

### 5. Design exploration `/designs/slate` — WCAG 1.4.10 Reflow

At 320×640 the page scrolls horizontally (`scrollWidth` 352, `clientWidth` 320). Reflow asks for 320 CSS pixels wide without two-dimensional scrolling. Desktop scan of this page had 0 axe violations.

### 6. Review by hand (axe incomplete, not a confirmed fail)

- Consent banner open: `#consent-body` overlaps other elements, so axe cannot measure its contrast. The node is gone once consent is accepted. Check the banner copy against the banner background by eye or with a picker.
- `/designs/quiet`: heading, support line, and links sit on a gradient. Axe cannot decide. Not in the public sitemap.
- Short or decorative step numbers (`aria-hidden`) are incomplete on the home page and the family steps in high contrast. They are hidden from assistive tech; no fix required unless the numbers are meant to be read.

## How to re-run

```bash
pnpm exec astro build --root apps/web
pnpm exec astro preview --root apps/web --host 127.0.0.1 --port 4321
BASE_URL=http://127.0.0.1:4321 pnpm a11y:web
```

`pnpm a11y:web` launches Playwright’s bundled Chromium (`apps/web/scripts/a11y-check.mjs`). If that browser is not installed, run `pnpm exec playwright install chromium`, or point the script at system Chrome. The gate does not resize, open the demo, or turn on high contrast. On `pnpm dev:web`, the Astro dev toolbar can cover the consent Accept button at 390px, so mobile checks should use the preview server.

Node detail for every scan is in `docs/a11y/2026-09-26-wcag-2.1-aa.json`.
