# WCAG 2.1 AA report — 26 September 2026

Audit of the Anchor website (`apps/web`) for later fixes. No code was changed in this pass.

- **Commit:** `4329836737c12c746d84f7cff55bce2031140a2e`
- **Engine:** axe-core 4.13.0 in Playwright Chromium, viewport 1280×900
- **Rules:** `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` (WCAG 2.0 and 2.1, Level A and AA)
- **Server:** Astro dev at `http://127.0.0.1:4321`
- **Gate:** `pnpm a11y:web` (`apps/web/scripts/a11y-check.mjs`) — **pass**, 10 routes × 2 consent states, 0 violations

## Verdict

The automated gate passes on first paint. It does not cover the demo after the chat log starts to scroll. That later state fails WCAG 2.1.1.

| Surface | Result |
| --- | --- |
| Public pages, cookie banner open and dismissed, 1280px | Pass (axe) |
| Home page at 320px CSS width | Fail (footer forces horizontal scroll) |
| Other public pages at 320px | Pass (no horizontal scroll) |
| Demo `/app` through “Send the photo”, “Yes, I’ll take part”, and “A little later — bring it back” | Fail once the private chat log overflows |
| Design prototypes `/designs/slate`, `/designs/linen`, `/designs/quiet`, `/designs/mist` | Pass |
| Design prototype `/designs/ink` | Fail (not linked from the live site) |

The live home page uses the Slate styles in `apps/web/src/pages/index.astro`. It is not the `/designs/ink` prototype.

## Fix 1 — private chat log is not keyboard-scrollable

**Rule:** `scrollable-region-focusable` (serious)  
**Criteria:** WCAG 2.1.1 Keyboard (A), 2.1.3 Keyboard (No Exception) (A)  
**Help:** https://dequeuniversity.com/rules/axe/4.13/scrollable-region-focusable

**When it appears**

1. Open `/app` and dismiss the cookie banner.
2. Click **Send the photo**, then **Yes, I’ll take part**, then **A little later — bring it back**.
3. axe then fails on the private chat log. It still fails after **Use a sample line**.

Earlier phases (`share`, `consent`, `wait`) pass. `pnpm a11y:web` only loads each page, so it never reaches this state.

**Where**

- Markup: both chat logs in `apps/web/src/components/MvpDemo.tsx` (`div.chat-log`, `role="log"`). The failing node is the private log (`ref={privateRef}`).
- Layout: `.chat-shell .chat-log` in `apps/web/src/components/MvpDemo.css` sets `max-height: min(26rem, 52vh)` on top of `.chat-log { overflow: auto }`.

**Why it fails**

The region scrolls and has no focusable content, and the region itself is not in the tab order. A keyboard user cannot move the overflow.

**Suggested fix**

Prefer letting the page scroll and dropping the inner `max-height` / `overflow: auto` on `.chat-log`, so there is no nested scrollport.

If the pane must stay a fixed height, make the log focusable and name it, for example `tabIndex={0}` and `aria-label="Private chat with Anchor"` (and the same for the family log). Do not rely on `role="log"` alone; a live region is not a keyboard scroll target.

**Gate follow-up**

Extend `apps/web/scripts/a11y-check.mjs` so `/app` is also scanned after those three clicks. Otherwise this regression stays invisible to `pnpm a11y:web`.

## Fix 2 — homepage footer scrolls sideways at 320px

**Criterion:** WCAG 1.4.10 Reflow (AA)  
**Not an axe rule.** Measured in Chromium at a 320×800 CSS viewport (the 1.4.10 width), cookie banner dismissed.

**When it appears**

On `/` only. `documentElement.scrollWidth` is 495px against a 320px viewport. `/how-it-works`, `/app`, `/family`, `/my-data`, `/privacy`, `/terms`, `/cookies`, and `/sitemap` stay at 320px. At 1280px the home page does not overflow.

**Where**

- Markup: the footer `<nav aria-label="Footer">` in `apps/web/src/pages/index.astro`.
- Layout: `.slate-footer nav` in `apps/web/src/components/designs/slate/slate.css` is `display: flex; gap: 1rem` with no `flex-wrap`. The eight links sit on one line about 475px wide. The nav has no class of its own; the overflowing element is that footer `nav`, not `.slate-nav` (the header wraps).

**Suggested fix**

Let the footer links wrap, and stack the footer on a narrow screen:

```css
.slate-footer nav {
  display: flex;
  flex-wrap: wrap;
  gap: 0.5rem 1rem;
}
```

At `max-width: 480px`, set `.slate-footer { flex-direction: column; }` so the sentence and the link row do not sit side by side in 320px. Re-measure `scrollWidth` at 320px after the change. Axe will not catch a regression here; the check has to be a viewport measurement.

## Fix 3 — ink prototype index numbers

**Rule:** `color-contrast` (serious)  
**Criterion:** WCAG 1.4.3 Contrast (Minimum) (AA)  
**Page:** `/designs/ink` only. Not in the sitemap and not used by the live home page.

Three `span.ink-action-index` elements (`01`, `02`, `03`) are `aria-hidden="true"` but still visible:

- Foreground `#787878`, background `#ffffff`
- 12px, normal weight
- Measured ratio **4.41:1** (needs **4.5:1**)

Darken the index color to about `#767676` or darker (a ratio check against `#ffffff` should be re-run). Because they are `aria-hidden`, this is a visual contrast bug, not a name bug.

## What passed

Public routes, each with the cookie banner open and with it dismissed (Accept):

`/`, `/how-it-works`, `/app`, `/family`, `/my-data`, `/privacy`, `/terms`, `/cookies`, `/sitemap`, and a missing URL that renders the 404 page.

Home (`/`) uses solid Slate colors, so axe could measure contrast and reported no violations. Inner pages use `BaseLayout` and a gradient on `body` in `apps/web/src/styles/tokens.css`. axe marks those nodes **incomplete** (it cannot sample a gradient, and the open cookie banner overlaps `#consent-body`). That is not a violation.

Worst-case pairs for the tokens still meet 4.5:1 for text, including muted ink `#3f4a48` on the darkest gradient stop `#d9ebe6` (about 7.4:1) and brand `#0f3d3a` on that same stop (about 9.7:1). Cookie-banner text on `#111111` also meets 4.5:1 (`#d6d1c7` body, `#e0c49a` links, `#f2f0eb` headings).

The secondary button border `#b9b3a8` is under 3:1 against the page. Those buttons are identified by their text, which meets 1.4.3, so this was not recorded as a 1.4.11 failure. Disabled controls at `opacity: 0.45` are inactive UI and are exempt from 1.4.3.
